# ADR-0002: the `.evidence` JSONL contract

- **Status:** Accepted
- **Date:** 2026-11-10
- **Ticket:** mact-f1w.1
- **Machine-readable form:** [`schema/evidence.schema.json`](../../schema/evidence.schema.json) (JSON Schema 2020-12, `schema_version: 1`), [`schema/run-meta.schema.json`](../../schema/run-meta.schema.json)
- **Checked by:** [`scripts/validate_evidence.py`](../../scripts/validate_evidence.py) and the fixtures
  under [`tests/e2e/testdata`](../../tests/e2e/testdata), plus `act-mcp validate-evidence` (mact-f1w.9),
  which implements the same rules and the same exit codes so CI can run either; the two are required to
  reach the same verdict, and `tests/evidence_contract.rs` holds them to it
- **Related:** ADR-0001 (tool contract), ADR-0003 (commit isolation / worktrees), ADR-0004 (run lifecycle)
- **Consumers inside the epic:** mact-f1w.9 (writer + `validate-evidence`), mact-f1w.10 (coverage extraction), mact-f1w.12 (benchmark extraction), mact-f1w.15 (e2e harness), mact-f1w.18 (human-facing format doc)

## Context

`act-mcp` runs a GitHub Actions job locally with `nektos/act` and writes one or two numbers per
run. Everything valuable about the project is *downstream*: another tool scans
`<workspace>/.evidence/` across many commits and plots benchmark and coverage history. The tool
result of `run_workflow` is a convenience; the files on disk are the public API. Once a second tool
reads them, a shape change is a breaking change, so the shape is decided before any evidence code is
written.

Constraints that drive the design:

- **act is a black box that loses files.** A job inside a container produces `lcov.info`,
  `benchmark.json`, etc. Those files only reach the host if the workspace is bind-mounted
  (`--bind`) or the job uploads them to act's artifact server (`--artifact-server-path`).
- **Runs are slow and can die.** A run may be cancelled, time out, or take the process down with it.
  A reader must never observe a half-written record, and a crashed run must not corrupt history.
- **Concurrent writers.** Two `act-mcp` processes pointed at the same workspace is a misconfiguration
  (ADR-0003 serialises runs per workspace), but the layout must not reward mistakes.
- **Numbers must stay comparable for years.** Percentages, aggregations and dedup policy decided today
  will be wrong tomorrow if we store derived values instead of raw inputs.
- **`schema_version` must survive the file layout being frozen.** Files are immutable (below), so a
  version bump means *mixed versions inside one directory*, forever.

## Decision

Numbered as in the ticket's "must pin" list. `MUST` / `MUST NOT` / `SHOULD` are normative.

### 1. Layout

#### 1.1 Tree

```
<workspace>/.evidence/
├── README.md                              # stub written by the writer, points here
├── benchmark/
│   └── <full-sha>/                        # 40 lowercase hex, the commit the run is attributed to
│       └── <run_id>.jsonl                 # one run's benchmark records, published atomically
├── coverage/
│   └── <full-sha>/
│       └── <run_id>.jsonl
├── runs/
│   └── <run_id>/
│       ├── meta.json                      # terminal-state manifest (see 1.3)
│       └── act.jsonl                      # act's own --json stream, verbatim (redacted), not versioned
└── incoming/
    └── <run_id>/                          # transient job payload scratch (see 3)
```

(`incoming/` is drawn under the evidence root because in the common case the run's working tree *is*
this workspace. When act runs in an ADR-0003 worktree the scratch directory lives in that tree
instead — see 3.1 — while everything durable stays here.)

- `.evidence/`, `.evidence/benchmark/`, `.evidence/coverage/`, `.evidence/runs/` are created on
  demand, mode `0755`, mode applied with an explicit `fchmod` (umask-independent).
- The **evidence root** is `--evidence-dir <path>` if given, else `$EVIDENCE_DIR`, else
  `<workspace>/.evidence`. Durable evidence *always* lands in the evidence root — never inside a
  temporary worktree created by ADR-0003, or it would be deleted with the worktree.
- The only files the writer ever creates under the root are `<run_id>.jsonl`, `meta.json`,
  `act.jsonl`, temp files matching `.<run_id>.jsonl.*.tmp`, and the `README.md` stub. Readers
  `MUST` skip dot-files and anything not ending in `.jsonl` / `meta.json`.
- `.evidence/runs/` and `.evidence/incoming/` are **not** commit-keyed and are **not** part of the
  cross-commit contract: a scanner walks `benchmark/` and `coverage/` only.

#### 1.2 Filename and `run_id`

`.evidence/<kind>/<full-sha>/<run_id>.jsonl` — one file per run, per kind. Both kinds use the same
shape (the ticket's `coverage/<sha>/<commit-short>-<run_id>.jsonl` variant was dropped: the short
SHA is already the directory name, and asymmetric names break `for f in */*.jsonl` style scans).

`run_id` is generated by the run supervisor (ADR-0004), but its **shape is pinned here** because the
layout depends on it being time-sortable:

```
run_id = UTC "YYYYMMDDTHHMMSSZ" "-" 6 lowercase hex
regex: ^[0-9]{8}T[0-9]{6}Z-[0-9a-f]{6}$      example: 20261110T004203Z-a1b2c3
```

So: **yes, filenames carry a UTC timestamp** — embedded in `run_id` rather than bolted on, which
means `ls` order == chronological order for free, and no separate timestamp field can disagree with
it. `run_id` is unique per run; nothing else in the name is needed for uniqueness.

Keying the path by the **full** commit SHA is what makes a cross-commit scan cheap: the scanner
`git log`s N commits, stats `<kind>/<sha>/` for each, and never opens a file for commits it does not
care about. Short SHAs are rejected (collisions, and `git rev-parse` in a scanner is a footgun).

#### 1.3 `runs/<run_id>/meta.json`

Written **last**, after act exits and after the JSONL records are published. Therefore:

- a present `meta.json` means the run reached a terminal state;
- a `runs/<run_id>/` directory *without* `meta.json` means act-mcp died mid-run, and everything in
  that directory (and any matching evidence file) is suspect.

Fields (see [`schema/run-meta.schema.json`](../../schema/run-meta.schema.json)): identity
(`schema_version`, `run_id`, `status`, `workflow`, `task`, `category`, `commit`, `host`), timing
(`started_at`, `finished_at`, `duration_ms`, `exit_code`), invocation (`act.argv` with secrets already
redacted, `act.version`, `act.pid`, `act.log`, `act.log_bytes`, `act.log_truncated`), payload
(`incoming.dir`, `incoming.files`, `incoming.removed`), output (`evidence[]` of
`{kind, path, records, truncated, malformed}`) and `warnings[]`.

`meta.json` is debug/audit context, **not** the load-bearing contract: it is how you answer "why is
there no coverage file for this run", and it is how `evidence[]` records "the run happened and
deliberately produced nothing" (empty `evidence[]`), which is otherwise indistinguishable from
"never ran".

`act.jsonl` is act's own log format, not ours. It is **not** covered by `schema_version`; its parser
contract is the golden fixture from mact-f1w.19 / mact-f1w.12. Secret values are redacted on write
(ADR-0001 / mact-f1w.13), so no file a run produces can contain a secret.

#### 1.4 `.evidence/README.md`

The writer creates a one-paragraph stub (if absent, never overwritten) saying: local build output,
safe to delete, format defined by ADR-0002, do not hand-edit.

### 2. Record envelope

Every line of every evidence file carries the same envelope, plus the per-kind fields of section 4.

#### 2.1 Nullability policy (pinned)

- A field is either **present with the correct type** or **absent**. A writer `MUST NOT` emit JSON
  `null`, and a validator rejects `null` anywhere: `null` and absence must never mean the same thing
  in two different files.
- "Unknown" is expressed by **omission**, never by a sentinel (`duration_ms: 0`, `exit_code: -1`,
  `unit: ""`, `path: "null"` are all forbidden). Consumers `MUST` treat absent as "not reported".
- Two envelope fields are commonly unknown and are therefore optional: `duration_ms`, `exit_code`.
- `additionalProperties: false`: an unknown field is a hard error, which is what makes "additive
  change" (section 7) meaningful for writers while readers stay forward-tolerant by policy, not by
  accident.

#### 2.2 Envelope fields

| field | type | required | notes |
|---|---|---|---|
| `schema_version` | int | yes | `const 1` in v1. See section 7. |
| `kind` | string | yes | **closed** enum `benchmark` \| `coverage`. |
| `run_id` | string | yes | pattern above; same value on every line of the file. |
| `commit` | string | yes | full lowercase hex SHA, `^[0-9a-f]{40}$`; must equal the `<full-sha>` directory. |
| `workflow` | string | yes | workflow identity as resolved by the validator: file basename without `.yml`/`.yaml` (e.g. `benchmark`). Never a path. |
| `task` | string | yes | job id that ran (`act -j <job>`), resolved, never re-derived from logs. |
| `category` | string | yes | **open** vocabulary (`benchmark`, `coverage`, future values); `^[a-z][a-z0-9_]*$`. In v1 `category == kind` always; kept because it records the *classification decision*, which may diverge from `kind` later (e.g. a benchmark run that turned out to emit a coverage file). |
| `run_status` | string | yes | enum `success` \| `failed` \| `cancelled` \| `timed_out` \| `error`. `success` = act exited 0. A workflow that ran and failed is `failed`, **not** an error. Evidence from non-`success` runs is written, not suppressed (aggregators filter). |
| `tool` | object | yes | `{name: "act-mcp", version: <server version>, act_version?: <act version>}`. `act_version` exists because an act upgrade moves timings and log shapes. |
| `started_at` | string | yes | UTC instant, always `Z` (never `+00:00`), fractional seconds optional: `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2]:[0-9]{2]:[0-9]{2}(\.[0-9]{1,6})?Z$`. Writers canonicalise to millisecond precision. |
| `duration_ms` | int ≥ 0 | no | whole-run wall duration, ms. Omitted when unknown. |
| `exit_code` | int 0..=255 | no | act's wait(2) code. Omitted when act produced no exit status (signalled, spawn failure). |
| `host` | string | yes | lowercased `gethostname()`. Advisory provenance; never a join key. |
| `flags` | string[] | no | machine-readable caveats, section 5. Unique, ≤ 8. |
| `extra` | object | no | advisory passthrough; **nothing may depend on a key here**. Anything load-bearing becomes a real field. |

Relative-path-shaped values (`path`, `source_path`, `meta.json` paths) share one rule and one
pattern: forward slashes, no leading `/`, no `~`, no `.` or `..` segment, ≤ 512 chars. Absolute host
paths (`/home/dev/…`, `/srv/…`, `C:\...`) `MUST NOT` appear anywhere in evidence — act mounts the
workspace at `/srv`, and leaking that into the record is both a portability and a privacy bug.

### 3. Getting job-produced payload out of the act container

#### 3.1 Decision: `--bind` plus a per-run incoming directory

act-mcp passes **`--bind`** and creates a per-run scratch directory:

- host: `<worktree>/.evidence/incoming/<run_id>/`, mode `0777`
- container: **the same absolute path** — `--bind` binds `<workdir>:<workdir>`, so there is no path
  translation on Linux (amended by ADR-0003 §15.1, which found that the `/srv/...` path spelled here
  originally was not the mount at all: a job writing to it wrote into its own container filesystem and the
  payload was lost with it)
- told to the job via two `--env` variables (values are the **container** paths, which under `--bind` are
  the host paths):
  - `ACTMCP_EVIDENCE_OUT=<worktree>/.evidence/incoming/<run_id>`
  - `ACTMCP_RUN_ID=<run_id>`

`<worktree>` is the directory act was pointed at (the primary workspace, or the ADR-0003 worktree for
a non-HEAD commit; ADR-0003 calls it `<tree>`). That is why the scratch dir is described relative to the
working tree while the *evidence root* of section 1.1 stays in the primary workspace: the scratch dir must
live inside whatever is bind-mounted; the durable JSONL must not.

`--bind` means containers write into the **real** working tree. Accepted consequences, and the
mitigations:

- a job can modify or delete tracked files → the workflow is the target repo's own CI job (trusted),
  and ADR-0003 owns isolation for untrusted commits; the payload directory is the only path
  act-mcp reads back.
- container-side file ownership is whatever uid the image runs as (root in most images, `nodeuser`
  in node images), so payload files may be owned by a foreign uid. The incoming dir is `0777` and
  deliberately **not** sticky, so act-mcp (the host user) can read `0644` payload files and unlink
  them regardless of owner. A payload file that is not world-readable yields the warning
  `payload_unreadable`; the run is not failed by it.
- act-mcp never globs the workspace for outputs and never follows a path out of the incoming
  directory: every payload path is canonicalised and prefix-checked.

`--no-bind` is supported as a degraded mode: extraction then relies on the in-band marker (section
5.2) and act-log timings only, and the run carries the warning `payload_transport_unavailable`.

**Rejected: `--artifact-server-path`.** act's artifact server requires the workflow to call
`actions/upload-artifact` (the contract would depend on the target repo's workflow content, so the
same local job would produce evidence in one repo and none in another), it lands artifacts in
act-generated directories unrelated to our per-run layout, needs an extra bound port for no benefit
on a loopback-only tool, and artifact upload failures do not fail the job — a missing-artifact run
looks like a successful run with no evidence. `--bind` requires nothing of the workflow beyond
"write a file where `$ACTMCP_EVIDENCE_OUT` points".

#### 3.2 Payload filenames a job must produce

`$ACTMCP_EVIDENCE_OUT` below is the directory of 3.1 — `/srv/.evidence/incoming/<run_id>` seen from
the container, `<worktree>/.evidence/incoming/<run_id>` seen from act-mcp. act-mcp looks for
**exactly** these names, in this precedence, and uses the **first one found**:

| kind | accepted filenames (precedence order, highest first) |
|---|---|
| coverage | `$ACTMCP_EVIDENCE_OUT/lcov.info`, `$ACTMCP_EVIDENCE_OUT/coverage-summary.json`, `lcov.info`, `coverage/lcov.info`, `coverage-summary.json`, `coverage/coverage-summary.json` |
| benchmark | `$ACTMCP_EVIDENCE_OUT/benchmark.json`, `$ACTMCP_EVIDENCE_OUT/benchmark.jsonl`, `benchmark.json`, `benchmark.jsonl` |

The place we *told* the job to write wins, so a stray file from an earlier build cannot shadow this
run's payload. The plain-name fallbacks at the workspace root exist because most coverage tooling
writes a conventional `coverage/lcov.info` and rewriting a target repo's tooling is not our business.
The `source`/`source_path` fields record which file was actually used, so a wrong guess is visible in
the data rather than silent.

**One source wins per run.** File-scope and total records come from a single source (the highest-precedence
file found) — never a blend of two tools' file lists, because lcov and istanbul disagree about which
files exist. Files that were found but *not* used are named in `meta.json` (`incoming.files`) with
the warning `coverage_source_shadowed`, so a human can tell the tools apart without two competing
`total` records.

#### 3.3 `benchmark.json` shape

```json
{ "metrics": [
  { "name": "tokenizer_throughput", "value": 184320.4, "unit": "ops/s",
    "labels": { "os": "ubuntu-24.04" }, "extra": { "tool": "hyperfine" } }
] }
```

- top level: object with a `metrics` array; a bare top-level array is accepted as shorthand.
- per entry: `name` (string) and `value` (finite number) required; `unit` (string), `labels`
  (flat string→string map) and `extra` (object) optional.
- An entry without a usable `name`/`value`, or with a non-finite, non-numeric or JSON-inexpressible
  value (`NaN`, `Infinity`, `"12ms"`) is rejected and counted in `evidence[].malformed`
  (`malformed_metric`). Unknown extra keys in an entry are ignored (forward compatibility).
- `benchmark.jsonl` alternative: one such entry per line, same rules — convenient for `jq` pipelines.
- Payloads are **untrusted input**: ≤ 8 MiB per file, ≤ 5000 metrics (excess is truncated with
  `flags:["truncated"]` and `evidence[].truncated = true`), ≤ 32 incoming files per run
  (`payload_too_large` beyond that). A payload may never re-attribute a run: `commit`, `run_id`,
  `workflow`, `task` always come from the tool call, never from file contents.

#### 3.4 Cleanup

After extraction, act-mcp deletes the payload files it successfully parsed (their numbers now live in
the JSONL) and keeps any it found-but-did-not-use or could-not-parse, all listed in `meta.json`. The
incoming directory is removed if it ends up empty. Because cleanup deletes *foreign-owned* files,
`meta.json` records `bytes` and `sha256` of what was consumed before deleting it.
Readers/scanners `MUST NOT` read `.evidence/incoming/`: it is scratch and may vanish at any time.

### 4. Metric record shapes

#### 4.1 benchmark

One metric per line:

```json
{"schema_version":1,"kind":"benchmark","run_id":"20261110T004203Z-a1b2c3","commit":"2f7c1a4b…","workflow":"benchmark","task":"hyperfine-bench","category":"benchmark","run_status":"success","tool":{"name":"act-mcp","version":"0.1.0","act_version":"0.2.68"},"started_at":"2026-11-10T00:42:03.417Z","duration_ms":94122,"exit_code":0,"host":"build-box-07",
 "name":"tokenizer_throughput","value":184320.4,"unit":"ops/s","labels":{"job":"hyperfine-bench","os":"ubuntu-24.04","runner":"self-hosted"},"sample":1,"source":"job_file","source_path":".evidence/incoming/20261110T004203Z-a1b2c3/benchmark.json"}
```

| field | type | required | notes |
|---|---|---|---|
| `name` | string | yes | metric name, verbatim from the job, or one of the built-ins `job_duration_s`, `step_duration_s`. |
| `value` | number | yes | any finite JSON number. Negative values are legal for deltas but never for `*_duration_s` (extractor rule, mact-f1w.12). Non-finite values are rejected before serialisation — JSON cannot express them. |
| `unit` | string | no | verbatim; act-mcp **never** converts, scales or invents a unit. Omitted ⇒ `flags` `MUST` contain `unit_missing`, and consumers `MUST NOT` combine values with differing (or missing) units. |
| `labels` | object | no | flat string→string, ≤ 16 entries, keys `^[a-z][a-z0-9_]*$`, values ≤ 128 chars. Values are **always strings** (numbers/bools stringified) so a `group by` never has to type-switch. Known keys: `job`, `step`, `os`, `runner`, `matrix`, `attempt`, `workflow`, `task`. Open key set. |
| `sample` | int ≥ 1 | no | present only when a job genuinely emitted >1 sample for the same `(name, labels)`; see 4.4. |
| `source` | enum | yes | `job_file` \| `in_band_stdout` \| `act_log`. |
| `source_path` | relpath | when `job_file` | the payload file the metric came from; omitted for `in_band_stdout` / `act_log` (whose input is `act.jsonl`). |
| `extra` | object | no | advisory. |

Coverage records `MUST NOT` carry `value`/`unit`/`labels`/`sample`; benchmark records `MUST NOT`
carry any coverage field (`scope`, `path`, `lines_*`, `branches_*`, `statements_*`, `functions_*`,
`reported_*`). The schema enforces this with `false` subschemas, so a "hybrid" record cannot be
written by accident. The words that appear in both tables (`name`, `source`, `extra`, `flags`) carry
the per-kind meaning given in each table.

#### 4.2 coverage

One source file (or the total) per line:

```json
{"schema_version":1,"kind":"coverage","run_id":"20261110T011507Z-d4e5f6","commit":"2f7c1a4b…","workflow":"coverage","task":"coverage","category":"coverage","run_status":"success","tool":{"name":"act-mcp","version":"0.1.0","act_version":"0.2.68"},"started_at":"2026-11-10T01:15:07.004Z","duration_ms":61233,"exit_code":0,"host":"build-box-07",
 "name":"total","scope":"total","lines_found":4120,"lines_hit":3581,"branches_found":1180,"branches_hit":946,"source":"lcov","source_path":".evidence/incoming/20261110T011507Z-d4e5f6/lcov.info"}
```

| field | type | required | notes |
|---|---|---|---|
| `scope` | enum | yes | `total` \| `file`. |
| `path` | relpath | when `scope == "file"`; forbidden for `total` | the source file, workspace-relative, `/` separators, container `/srv/...` normalised away. Identity of a file record is `path`, not `name`. |
| `name` | string | no | label, conventionally `"total"` on total records; omitted on file records. |
| `lines_found` / `lines_hit` | int ≥ 0 | one complete pair, or `statements_*`, or `reported_percent` | raw numerators. `hit ≤ found` (extractor rule; the schema cannot express cross-field comparisons). |
| `branches_found` / `branches_hit` | int ≥ 0 | optional, **co-required pair** | omitted when the format reports no branches (e.g. generated files). |
| `statements_found` / `statements_hit` | int ≥ 0 | optional, co-required pair | istanbul statements are a *different unit* from lines; keep them separate, never average the two. |
| `functions_found` / `functions_hit` | int ≥ 0 | optional, co-required pair | istanbul `functions`. Reserved in v1 so adding it later is additive. |
| `reported_percent` | number 0..=100 | only for percent-only sources | see 4.3. Forbidden together with any `*_found`/`*_hit`; requires `reported_measure` and `flags:["percent_only"]`. |
| `reported_measure` | enum | with `reported_percent` | `lines` \| `statements` \| `branches` \| `functions` \| `unknown`. A table column nobody labelled is `unknown`, not a guess; a bare `Coverage: 87.4%` is read as `lines`, because a tool that prints one unqualified percentage prints the one its own threshold gate evaluates, and every reporter observed (coverage.py, `nyc --check-coverage`, `jest --coverage`) means lines there — the shape `expected/coverage-log-scrape.jsonl` pins. |
| `source` | enum | yes | `lcov` \| `coverage_summary` \| `log_scrape`. |
| `source_path` | relpath | for `lcov`/`coverage_summary` | omitted for `log_scrape` (its input is `act.jsonl`). |

Supported in v1: **lcov** (`SF:`/`DA:`/`LF:`/`LH:`/`BRDA:`/`BRF:`/`BRH:`, repeated `SF` blocks summed
per path), **istanbul `coverage-summary.json`** (`lines`/`statements`/`branches`/`functions`
`covered`/`total`). **Cobertura `coverage.xml` is explicitly unsupported** — `coverage.xml` is not in
the filename table and mact-f1w.10 returns a clean `unsupported_format` rather than guessing.
A format that is added later is an additive change.

The total record is the **source's own total**: for lcov the sum over every `SF` block, for
istanbul its `total` entry. Either can exceed the sum of the run's `scope:"file"` records when the
tool instrumented files that live outside the workspace (`node_modules` is the everyday case) — no
`relpath` can name those, so they get no file record while still belonging to what the run
measured. The extractor reports how many it dropped (`coverage_paths_outside_workspace` in
`meta.json`'s `warnings[]`) rather than silently renumbering the total.

#### 4.3 Percentages are recomputed by consumers (pinned)

- Evidence stores **raw numerators and denominators only**. No record stores a line rate next to the
  counts it came from; two sources disagree on rounding and we refuse to arbitrate.
- Consumers compute `rate = hit / found`. When `found == 0` the rate is *vacuous*: a consumer that
  must print a number prints `100%` (the lcov/istanbul/cobertura convention), and a consumer that
  ranks or averages `SHOULD` exclude zero-denominator entries rather than letting an empty generated
  file move the number.
- Cross-run or cross-commit totals are computed by **summing numerators and denominators over file
  records**, never by averaging per-file percentages. The `scope:"total"` record of a run may be used
  directly as that run's total. Within one run the two agree exactly, with the one exception above:
  source files outside the workspace are in the total and in no file record.
- A percentage with no raw counts is possible **only** via `reported_percent`, which is possible only
  for `source: "log_scrape"` (last resort), is always flagged `percent_only`, and always names its
  `reported_measure`. Inventing a denominator (`874/1000`) to make a scraped percentage look raw is
  forbidden. A scanner `MUST` be able to filter these out (`flags` has `percent_only`).

#### 4.4 Append-only, dedup and aggregation ownership

- **act-mcp appends; it never edits or aggregates.** Each run appends files (section 6.2); it never
  updates a previous run's numbers, never deletes history, and never computes a mean, a percentile or
  a "best" value.
- Within **one run**, the writer does not emit two records with the same `(name, labels, value,
  source)` — an accidental duplicate from a chatty job. Genuine repeats of `(name, labels)` with
  different values are **samples** and are all kept, numbered `sample: 1..n`.
- Across runs, duplicates are *data*, not a bug: two runs of the same commit are two measurements
  (possibly of different noise levels), and the scanner chooses. The scanner owns dedup policy,
  percentiles, outlier rejection, regression detection and unit reconciliation. That is a non-goal of
  this epic (see epic "Non-goals") and the reason no aggregate lives here.
- A record is identified for diffing by `(commit, kind, run_id, name, labels)` for benchmark and
  `(commit, kind, run_id, scope, path)` for coverage.

### 5. Signals: `source`, `flags`, warnings

#### 5.1 Vocabulary

| `source` | kind | meaning | authority |
|---|---|---|---|
| `job_file` | benchmark | payload file written through the bind mount | authoritative |
| `lcov` | coverage | parsed `lcov.info` | authoritative |
| `coverage_summary` | coverage | parsed istanbul `coverage-summary.json` | authoritative |
| `in_band_stdout` | benchmark | `ACTMCP_BENCHMARK` marker scraped from act's log | convenience, lower precedence |
| `act_log` | benchmark | timing derived from act's own `--json` timings | context, always emitted |
| `log_scrape` | coverage | percentage scraped from act's log text | last resort, `percent_only` |

Known `flags` (open vocabulary; unknown flags are ignored, never an error):

| flag | meaning |
|---|---|
| `unit_missing` | benchmark record whose job reported no unit (schema-enforced when `unit` is absent) |
| `percent_only` | coverage record that has a percentage and no raw counts |
| `low_confidence` | derived from text scraping rather than a machine-readable file |
| `truncated` | the per-run metric cap was hit; every record of that run carries it, and `meta.json.evidence[].truncated` is true |

`meta.json` `warnings[]` codes (machine-readable, open vocabulary):
`no_coverage_found`, `parse_failed`, `unsupported_format`, `payload_too_large`,
`payload_unreadable`, `payload_transport_unavailable`, `coverage_source_shadowed`,
`malformed_metric`, `marker_cap_reached`, `truncated`.

None of these ever change `run_status`: extraction problems never fail a run. A failed act run still
writes its evidence with `run_status: "failed"` so a benchmark dip caused by a broken run is
*visible and filterable* rather than missing.

#### 5.2 In-band stdout marker (decision: **yes, but files are the contract**)

A benchmark job may additionally print marker lines to stdout:

```
ACTMCP_BENCHMARK {"name":"cold_start_ms","value":412.5,"unit":"ms","labels":{"step":"Run benchmark"}}
```

Grammar (pinned): after optional leading whitespace, the line starts with the literal
`ACTMCP_BENCHMARK ` and the remainder, up to the last `}` on that line, is one compact JSON object
with the same per-metric shape as a `metrics[]` entry. Regex:
`^[ \t]*ACTMCP_BENCHMARK (\{.*\})[ \t]*$` (greedy to the final `}`; one metric per line, no
multi-line records).

Rules:

- Anchoring at line start is deliberate: it avoids matching a README or a `cat`-ed source file that
  merely mentions the marker. Documented ambiguity, accepted because the marker is a convenience,
  not the primary path.
- Scraping runs over act's `--json` log *after* secret redaction (mact-f1w.8 / mact-f1w.13), so a
  secret can never be laundered into evidence via a marker line.
- Where the scan looks: act writes a step's stdout into the JSON log's `msg` field (one line per
  process write, but a single `msg` may hold several), so the grammar is applied to each line of
  `msg` — and of the `Output`/`Error` spellings this log has used — rather than to the JSON log line,
  which never starts with the literal. A log captured without `--log-format=json` is scanned line by
  line instead, which is why the scan must never depend on the JSON form.
- Malformed marker lines are counted (`malformed_metric`) and ignored; they never fail a run. Cap
  5000 marker lines per run (`marker_cap_reached`). A line that starts with the literal and carries
  no JSON behind it is not a malformed marker — it does not match the grammar at all, so it is a line
  that mentions the marker, the same way a README does.
- **Precedence:** a `job_file` metric wins over an identical `in_band_stdout` metric (same
  `name` + `labels` + `value`); the duplicate is dropped and the surviving record keeps
  `source: "job_file"`. Use the marker when a job cannot write files (no `--bind`, read-only fs, a
  runner whose tooling only prints); do not use it as the only path if the job can write a file.
- There is **no coverage marker** in v1. Coverage comes from a real file, or from last-resort
  `log_scrape` of whatever the job already printed. A percentage typed into a marker would be a third
  source of truth for a number we already refuse to store.

#### 5.3 act's own durations are always recorded (decision: **always, not only when the job is silent**)

For every benchmark run, act-mcp emits `job_duration_s` (labels `job`) and `step_duration_s`
(labels `job`, `step`) with `source: "act_log"` and `unit: "s"` (millisecond precision, e.g.
`88.234`), derived from the captured `--json` timings. Rationale: every benchmark run then leaves at
least one row, so "did it run at all, and how long did it take" is answerable even for a job that
emits nothing, and a benchmark regression can be compared against total job time in the same file.

How the derivation reads the log (pinned by mact-f1w.12, because two implementations of "the run's
duration" that disagree would be worse than none):

- A line counts for this run when it carries `jobID` (or `job`) equal to the requested job id; a line
  naming no job at all is ambient to this run, and a line naming a **different** job — a `needs:`
  dependency act ran through the same log stream — is dropped. None of a dependency's steps may
  become this run's duration.
- One `step_duration_s` row per step that logged a duration, including act's own `Set up job` and
  `Complete job` steps: act's `executionTime` is the step's own and act does not fold its setup into
  the workflow step, so a row per step is what lets `job_duration_s` be the sum of the emitted step
  rows. A step that logged a duration but no name contributes to the total and gets no row of its own
  (a label that says nothing groups nothing).
- `job_duration_s` is that sum when at least one step logged a duration. Otherwise — act killed the
  run mid-step, so nothing ever logged a completion — it is the span of the run's own log timestamps,
  which act writes at whole-second precision: a coarser number, and honest about being one.
- Suppression is per label set: a `job_file` or `in_band_stdout` metric named `job_duration_s` (or
  `step_duration_s` for a given `step`) suppresses the act-derived row with the same `(name, labels)`
  only. act measured the whole job and the workflow measured a step are different measurements and
  both stay.

If a job emits its own `job_duration_s`, the **job's value wins** and the act-derived one is
suppressed — a job measuring its own phase beats act measuring the whole job, and silently keeping
both would double-count a duration.

Note the deliberate asymmetry: the envelope's `duration_ms` is integer **milliseconds** (plumbing),
the metric names are human-facing **seconds** (`*_s`). The name carries the unit precisely so the
metric is self-describing.

One consequence of the caps in §3.3 worth stating plainly: the per-run metric cap is shared by the
three sources, so a job that emits 5000 marker lines leaves no room for these fallback rows. Every
record of such a run carries `truncated`, which is the point of the flag — a consumer must never sum
what survived and call it the run.

### 6. Concurrency, atomicity, creation

#### 6.1 Serialization rules

- One compact JSON object per line, no insignificant whitespace, key order stable per record type
  (stable enough that a golden-file test is meaningful).
  "Stable" needs a definition, or two writers produce different bytes for the same record and the
  golden test is meaningless; it is given one here rather than left to the first implementation.
  - **Top-level keys** appear in the order this ADR lists them: the §2.2 envelope fields in table
    order (`schema_version`, `kind`, `run_id`, `commit`, `workflow`, `task`, `category`,
    `run_status`, `tool`, `started_at`, then `duration_ms`/`exit_code` when present, then `host`),
    then that `kind`'s payload fields in the order §4 presents them, with `source`, `source_path`,
    `flags`, `extra` last in that order. An absent optional field is omitted, not nulled (§2.1), so
    the order is of *present* fields.
  - **Keys inside an object** (`labels`, `extra`, `tool`'s members) are written in ascending
    code-point order. A JSON object's members are unordered, so the writer does not preserve a
    producer's insertion order there; sorting is what makes the output a function of the record and
    nothing else.
  - Consequences, both of which a test pins: the order is a property of the record type and not of
    whoever wrote the file, and re-parsing a published file and re-serializing it yields identical
    bytes.
- UTF-8, no BOM, LF only (no CR, ever), no NULs, no embedded raw newlines, trailing LF at EOF
  **required** — a file whose last byte is not LF is a torn write by definition and a checker `MUST`
  fail it.
- Strict RFC 8259 JSON: no `NaN`, `Infinity`, comments, or trailing commas.
- One file carries exactly one run: every line shares `run_id`, `commit`, `workflow`, `task`.

#### 6.2 Atomic publish: **one file per run, immutable after publication**

This is the core mechanism. To publish a run's records:

1. build the whole record list in memory;
2. write it to a temp file **in the destination directory** named
   `.<run_id>.jsonl.<random>.tmp`;
3. `fsync` the file;
4. `rename()` it to `<run_id>.jsonl` (same filesystem ⇒ atomic);
5. `fsync` the directory.

A reader therefore never sees a partial record or a half file: `rename` is atomic, and the file only
becomes visible with its final name and full content. Temp files are invisible to readers (leading
dot, `.tmp` suffix) and are safe to delete for any run that has a `meta.json`.

**Because each file is exactly one run, "append-only" happens at the directory level**, and we get the
stronger guarantee: a published file is never opened for writing again. That removes the classic
append hazards (interleaved records from two writers, `O_APPEND` line splitting across filesystems,
readers seeing `st_size` mid-write) rather than mitigating them, and makes a crashed run's damage
scope exactly one file. A writer `MUST NOT` open an existing `<run_id>.jsonl` for writing; if the
destination already exists the writer fails with `evidence_path_exists` and leaves the tree alone
(reaching this means a `run_id` collision, which is a bug worth surfacing, not silently merging).

Rollback = delete the file. There is no read-modify-write path anywhere in the writer, which is also
what makes section 7's version policy trivially safe.

#### 6.3 Single writer

- In-process: one writer task per destination path, serialised by an async mutex keyed on the
  canonical destination path. Only one act run is ever in flight per workspace anyway.
- Cross-process: the workspace run lock of ADR-0003/0004 is the single-flight gate. The evidence
  layer adds no `flock` of its own; it relies on that lock plus the immutability rule above. A second
  act-mcp pointed at the same workspace gets `workspace_busy`, and two runs can never race to the same
  path (different `run_id` ⇒ different file even if the lock were bypassed).
- Symlinks and traversal: every path built from caller-controlled input (commit, run_id, workflow) is
  canonicalised and prefix-checked against the evidence root; a component that is a symlink, or a path
  that resolves outside the root, is rejected (`evidence_path_escape`). `.evidence` is never written
  through a symlink, and the writer never creates a path containing `..`.

#### 6.4 Absent `.evidence`, permissions, gitignore

- If the evidence root does not exist, create it (and the `benchmark/`, `coverage/`, `runs/`
  subtrees) with mode `0755`, `fchmod`-applied. `EVIDENCE_DIR` / `--evidence-dir` override it (the
  override is canonicalised and prefix-checked like any other caller-controlled path).
- `.evidence/` is machine-local build output and **is gitignored by default**:
  - this repository ignores `.evidence/` (a developer running the server on this repo must not dirty
    it);
  - when act-mcp creates an evidence root inside a *target* workspace that is a git repository, it
    appends `.evidence/` and `.act-mcp.lock` (the workspace run lock of ADR-0003 §6) to that workspace's
    `.gitignore` — idempotent (skip if already ignored,
    checked with `git check-ignore`), under a `# act-mcp evidence (local only)` marker comment,
    never reordering or rewriting existing content, and skipped silently if the workspace is not a
    git repo or `.gitignore` is not writable.
  - The rationale for committing to *commit-keyed*, gitignored evidence: evidence travels by scanning,
    not by git. Committing it would put generated files in the diffs of the repos we instrument, and
    the SHA-keying already handles identification without needing versioning.

### 7. Compatibility policy

`schema_version` is a flat, monotonically increasing integer, currently `1`. It is stamped on every
record and on `meta.json`.

- **Additive ⇒ no bump.** Adding an optional field, adding a member to an *open* vocabulary
  (`category`, `flags`, `source`, `warnings`), adding a newly supported coverage format, or adding a
  new accepted payload filename. A v1-reading consumer of v1 data with extra fields `MUST` still work
  — and the `source: "cobertura"` example is exactly why unknown values must be tolerated rather than
  fatal.
- **Breaking ⇒ bump.** Changing the type or meaning of an existing field, making an optional field
  required, renaming or removing a field, closing an open vocabulary, changing the *closed* `kind`
  enum, or changing the layout, filename convention, path keying, or the meaning of an existing
  `flag` (e.g. if `truncated` ever meant something else). A new `flag` is additive; redefining one is
  not.
- **Writers** only ever emit the version they were built with (`SCHEMA_VERSION`, a compile-time
  constant); there is no code path that re-emits a foreign version, and no read-modify-write path
  (6.2) that could accidentally do so. **The question "does the server refuse to write a version it
  does not know how to read?" resolves to: it cannot even try.**
- **Readers must refuse what they cannot understand.** `act-mcp validate-evidence` (mact-f1w.9) `MUST`
  exit non-zero on a record whose `schema_version` it does not know (`unsupported_schema_version`) and
  `MUST NOT` ever "upgrade" a file in place. It is a strict dev/CI tool: unknown field, unknown `kind`,
  unknown `schema_version` are all hard errors.
- **Downstream scanners** are separate programs with their own policy, and the recommended one is
  *permissive on values, strict on shape*: ignore unknown `category`/`flag`/`source` members and
  unknown fields, skip (with a count) records whose `schema_version` is newer than the scanner's, and
  treat a structurally unknown record as an error to report. Since files are immutable, a version bump
  leaves **mixed versions in one directory forever**; a scanner `MUST NOT` assume one version per
  directory or per commit.
- The contract is the schema file plus this ADR. An implementation that finds a hole `MUST` update
  both in the same change (mact-f1w.9 says the same thing); inventing a second shape in code is the
  failure mode this ADR exists to prevent.

## Consequences

**Good**

- A scanner's hot path is `git log` + `stat` on `<kind>/<sha>/` — no parsing of unrelated commits, no
  index to maintain, no lock to fight over.
- Torn writes and half-written runs are structurally impossible, not improbable; a crashed run costs
  one file and one `meta.json` gap.
- Because nothing is derived, a better aggregator can be written later against years of raw data and
  get different (better) answers without re-running anything.
- Payload transport requires nothing of the target repo's workflows beyond an env var, and works with
  any coverage/benchmark tool that can write a file.
- `source` + `flags` make provenance queryable, so "trust only lcov-derived totals" is a filter, not a
  folklore rule.

**Costs**

- `--bind` hands containers write access to the working tree. Accepted for a local tool whose jobs are
  the repo's own; isolation of untrusted commits is ADR-0003's problem, and `--no-bind` degrades rather
  than breaks.
- One file per run means many small files (one per kind per run) rather than two big logs; inode churn
  and `ls` noise are the price. Directories stay small per commit.
- Immutability means the same run cannot be corrected in place; a wrong record is corrected by a later
  run and a scanner-side "prefer newest" rule.
- The writer must create `0777` scratch dirs and delete files owned by container uids — ownership is
  the fiddliest part of the whole design (see 3.1).
- The in-band marker is a second ingestion path and will produce junk lines sometimes; it is
  countable and lowest-precedence, but it is real complexity that a files-only contract would not have.

## Considered alternatives

- **One JSONL file per commit, appended across runs** (`benchmark/<sha>.jsonl`). Cheaper on inodes,
  but every atomic-append story then needs either a rewrite-and-rename of the whole file (O(n) per run,
  and wrong under any concurrency) or `O_APPEND` write-then-fsync with a mutex per path and a
  cross-process `flock`. One-file-per-run gets atomicity from `rename` and needs neither.
- **Coverage filename carrying `<commit-short>-<run_id>.jsonl`** (the ticket's proposal): redundant with
  the directory and asymmetric with `benchmark/`.
- **Timestamp-in-filename as a separate field** (`<run_id>-<utc>.jsonl`): the timestamp is already the
  `run_id` prefix; a second copy can only drift.
- **Artifact server transport** (`--artifact-server-path`): rejected in 3.1 — makes evidence depend on
  the target repo's workflow content, opaque landing directories, extra port, silent failures.
- **Files-only ingestion** (no stdout marker): cleaner, but then a job on a read-only or non-bind
  setup produces nothing at all, and the fallback we would end up adding anyway is `log_scrape`, which
  is strictly worse than a structured marker.
- **Storing percentages/ratios** in records: rejected — rounding policy, weighted-average traps and
  source disagreement would all become part of the contract. Store numerators and denominators.
- **A third `kind: "notice"`** for truncation/meta records: `kind` stays a closed two-value enum that
  mirrors the directory; truncation is a `flag` on real records plus `meta.json`, which keeps every
  line in `benchmark/` parseable as a benchmark record.
- **`null` for unknown** (with `required` fields everywhere): rejected in favour of omission — `null`
  in JSONL means nothing extra and every consumer would need a two-valued "absent-or-null" type.
- **Semver-style `major.minor` versions**: a flat integer matches "additive is free, meaning-change
  bumps" without pretending we can express a compatibility range in a number.

## Open questions (owned elsewhere)

- `run_id` generation, uniqueness and the `--evidence-dir` flag surface — ADR-0004 / mact-f1w.11.
- Whether act's `--json` timings are per-step precise enough for `step_duration_s` on matrix jobs —
  mact-f1w.19 captures the real log shape; if per-step timings turn out to be unavailable, only
  `job_duration_s` ships and that is an additive narrowing, not a version bump.
- Retention/pruning of `.evidence/runs/` (log bytes accumulate faster than records): a scanner-side or
  operator concern (a cron that deletes `runs/<run_id>/` older than N days is safe because the JSONL
  contract does not live there); revisit if real usage shows it hurting.
- Whether `functions_found`/`functions_hit` earn their place — reserved now so that answering "no" later
  is the only breaking move left unused.
